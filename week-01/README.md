- VPS: 2 vCPU, 4 ГБ RAM, 50 ГБ NVMe, Ubuntu 24.04
- Сервер достался «с историей»: на нём уже стояли Wazuh, агент Zabbix и fail2ban со старым конфигом
- Доступно RAM на старте: 1,5 ГБ из 3,8

## 28.09 — доступ и файрвол

### Что сделал
- [x] Создал пользователя `lexus` с правами sudo — работаю не под root
- [x] Вход по SSH-ключу ed25519, passphrase хранится в Keychain macOS
- [x] Запретил вход под root и по паролю (`/etc/ssh/sshd_config.d/00-hardening.conf`)
- [x] Включил ufw: deny incoming, разрешён только SSH (22/tcp)

### Зачем
- **Ключ вместо пароля.** Пароль можно подобрать, подсмотреть или взять из утёкшей базы. Ключ ed25519 подобрать нереально, а приватная часть никогда не передаётся по сети — сервер только проверяет подпись.
- **Без root.** Root — первая цель ботов, и любая ошибка под root бьёт по всей системе. Под обычным пользователем привилегии берутся через sudo осознанно и точечно.
- **Файл `00-hardening.conf`.** SSH применяет первое найденное значение, а в облачных образах Ubuntu есть `50-cloud-init.conf`, который может включать пароли. Префикс `00` гарантирует, что мои настройки читаются первыми.

### Что нашёл
- В ufw открыт 10050/tcp — агент Zabbix от Timeweb (мониторинг хостинга). Оставил осознанно.

## 30.09 — fail2ban и автообновления

### Что сделал
- [x] fail2ban для sshd: `backend = systemd`, бан на 1 час после 5 неудачных попыток за 10 минут
- [x] Проверил автообновления безопасности (unattended-upgrades) — включены
- Попыток входа под несуществующими пользователями только за 30.09: **1342**
- Первый бан — через несколько минут после запуска

### Зачем fail2ban, если пароли отключены
- **Второй рубеж.** Если пароли когда-нибудь включат по ошибке или появится сервис с паролем, fail2ban уже стоит.
- **Уязвимости в самом SSH.** Многим эксплойтам нужны тысячи подключений; бан после 5 попыток их срывает.
- **Шум и ресурсы.** Тысячи попыток в день нагружают сервер и прячут реальные проблемы в логах.
- **Дальше пригодится.** Когда появится nginx, те же боты придут туда.

### Что сломалось и как починил
- **Симптом:** после настройки fail2ban в состоянии `failed`, ошибка `option 'bantime' in section 'DEFAULT' already exists`.
- **Причина:** на сервере уже был fail2ban (работал с 19.08), а `jail.local` оказался полной копией `jail.conf` на 988 строк. Мой блок добавился к нему — получились дубли `[DEFAULT]` и `[sshd]`.
- **Диагностика:** `journalctl -u fail2ban`, проверка конфига `fail2ban-client -t`.
- **Решение:** сохранил старый файл в `.bak`, переписал `jail.local` начисто — 10 строк вместо 988.
- **Вывод:** в `.local` держу только свои изменения. После перезагрузки проверяю, что сервисы реально `active`, а не верю, что «я же запустил».

## 30.09 — аудит памяти: Wazuh-призрак

- После перезагрузки на «пустом» сервере было занято 2,3 ГБ RAM — в 4–5 раз больше нормы.
- `ps aux --sort=-%mem` показал полный комплект Wazuh: indexer (1,4 ГБ), dashboard, manager.
- В systemd их не было — Wazuh работал **в Docker** (single-node через docker compose). Первое «удаление» через apt ничего не дало: контейнеры поднимались после каждого ребута.
- Остановил контейнеры и отключил их автозапуск: доступная память **1,5 → 3,4 ГБ**.

### Уроки
- Docker публикует порты в обход ufw — файрвол не защищает то, что торчит из контейнеров.
- `docker ps 2>/dev/null` без sudo ничего не показал: `2>/dev/null` спрятал ошибку доступа. Глушить ошибки — значит прятать от себя правду.
- Процессы контейнеров видны на хосте с числовыми UID, поэтому `ps` подставляет имена пользователей хоста. Это совпадение номеров, а не взлом.

## Главные команды недели

```
adduser / usermod -aG sudo         # пользователь
ssh-keygen -t ed25519              # ключ
sshd -t / sshd -T                  # проверка конфига SSH
ufw default deny incoming          # файрвол
fail2ban-client -t / status sshd   # fail2ban
journalctl -u <сервис>             # логи сервиса
ps aux --sort=-%mem                # кто ест память
docker compose down -v             # снести стек с томами
crontab -e / crontab -l            # расписание
```
